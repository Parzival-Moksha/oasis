# Oasis agent engine

Runs Claude Code sessions (and, since 2026-11-18, Hermes agents: see "Hermes agents" below) as Oasis agents. Each agent you own is one long-lived `claude -p` stream-json process. The engine discovers your existing sessions, can mirror any of them read-only, and accepts Claude Code `type: "http"` hooks. Everything is bridged to the Oasis page over one WebSocket.

- Start it from the af_oasis root with `pnpm dev:engine`, next to `pnpm dev`.
- It listens on `127.0.0.1:4530` (`/ws`, `/health`, `/hook`, `/api/*`). Requests must come from a loopback Host and, when they carry an Origin, a loopback Origin. That stops other websites and DNS rebinding.
- The roster of agents you spawned lives in `data/agent-engine.local.json` (gitignored), and agents come back with `--resume` after a restart.
- Smoke test (0 turns): with the engine running, `node packages/oasis-agent-engine/scripts/smoke.mjs basic`. It only touches the scratch agents in `sandbox/`.

This package grew out of the 7c_oasis spike (`C:/7c_oasis/spike`). The schema and findings below were verified against Claude Code 2.1.316 on Windows.

## How an agent process is spawned

```
claude.exe -p --input-format stream-json --output-format stream-json --verbose
  --include-partial-messages      # text deltas (+ system/status "requesting")
  --replay-user-messages          # echo of each user message at the moment the CLI takes it in
  --forward-subagent-text         # subagent text too, tagged with parent_tool_use_id
  --permission-prompt-tool stdio  # permission prompts, AskUserQuestion, ExitPlanMode -> host
  [--model haiku|sonnet|opus|<id>] [--permission-mode ...] [--effort ...]
  [--mcp-config <tmp>/oasis-agent-engine-mcp-*.json]  # world tools: the Oasis MCP server (worldtools.js), unless the Oasis plugin brings it
  --allowedTools mcp__oasis__place_object,...,mcp__plugin_oasis_oasis__place_object,...  # its free tools run without a card, under either name
  --resume <id> [--fork-session]  # existing session (found in any project dir)
  | --session-id <new uuid>       # new agent: the id is known before the first turn
```

- **Windows:** `%APPDATA%\npm\claude.cmd` only runs `node_modules\@anthropic-ai\claude-code\bin\claude.exe %*`. `claude.js` parses the shim and spawns the exe directly with `shell:false`. That avoids cmd.exe quoting, and `kill()` reaches the real process. If parsing fails, it falls back to `claude.cmd` through a shell.
- **Env:** every `CLAUDECODE` / `CLAUDE*` variable is dropped, except `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_GIT_BASH_PATH`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK/VERTEX` and `CLAUDE_CODE_MAX_OUTPUT_TOKENS`. The desktop app injects about 30 of these (session id, messaging socket and token, entrypoint, effort...). With them stripped, the children ran as normal `sdk-cli` sessions on the subscription (`apiKeySource:"none"`).
- **Sandbox agents** also get `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. `spike/sandbox` sits inside the 7c_oasis git repo, so without it a scratch agent loads the repo's `CLAUDE.md` **and the owner's 7c_oasis auto-memory**. `get_context_usage` listed `memory_files` = repo CLAUDE.md, the sandbox CLAUDE.md, and `~/.claude/projects/C--7c-oasis/memory/MEMORY.md`.
- The owner's global hooks (agentcraft) also run in every child. That's expected, since these are real Claude Code sessions.
- **World tools** (2026-11-08): every agent gets the Oasis MCP server (`http://127.0.0.1:4516/api/mcp/oasis`, override with `OASIS_WEB_URL`) through `--mcp-config`, so Anorak Pro in 7c_oasis, Rick and Tyler can see and build in the world, not only sessions started in af_oasis. Before this, only folders with af_oasis's `.mcp.json` had it. Looking, placing, lighting and screenshot tools are pre-allowed. Tools that spend credits (`generate_*`, `conjure_*`, `craft_scene`), switch or wipe the owner's world (`load_world`, `create_*world`, `clear_world`) or delete library files still ask. Opt out per agent with `worldTools: false` in the spawn command or roster. The Oasis page server must be up when the agent starts, or the server shows as `failed`. `node scripts/smoke.mjs world` checks it (1 haiku turn). The CLI also accepts `control_request {subtype:"mcp_set_servers", servers:{...}}` on a live process (found in the binary, used by the SDK's `setMcpServers`). Not used yet; it would toggle the tools without a respawn.
- **World tools from the plugin** (2026-11-10, 2.1.318). The Oasis plugin (`plugins/oasis/.mcp.json`) ships the same server, so every session on the machine has it, the desktop app included. A plugin's MCP server is named `plugin:<plugin>:<server>` and its tools `mcp__plugin_<plugin>_<server>__<tool>`: here `plugin:oasis:oasis` and `mcp__plugin_oasis_oasis__place_object`. `pluginShipsWorldTools(cwd)` reads `~/.claude/plugins/installed_plugins.json` (a plugin named `oasis`), `enabledPlugins` in the user's settings and the folder's `.claude/settings*.json`, and the installed copy's `.mcp.json` (same URL as the engine's). When all three hold, the engine passes no `--mcp-config`; either way it pre-allows the free tools under both names. Checked at each spawn, so an install or update needs no engine restart. **The CLI drops a plugin server whose URL equals a server from `--mcp-config` or a project `.mcp.json`** (that one wins, `source: dynamic` / `project`, tools stay `mcp__oasis__*`), so an agent never sees the tools twice; af_oasis's own `.mcp.json` uses the same `127.0.0.1` URL for that reason. `claude plugin update oasis@oasis` refreshes the installed copy after the plugin changes (it is a cached copy, not the repo folder).
- **Eyes** (2026-11-10). With `eyes` on for an agent, `send` first asks the Oasis page for a picture from that agent's avatar and puts it in the same user message: `content: [{type:"text", text}, {type:"image", source:{type:"base64", media_type, data}}, {type:"text", text:"[Oasis eyes: ...]"}]`. Pages that can take one say `canSee`; the engine sends them `{type:"eyes.request", requestId, agentId}` and the first `eyesFrame {requestId, data, mediaType}` wins (`VillageEyes.tsx` renders the scene once at 800x450, fov 100, from the desk toward the owner; about 30 KB, about 500 tokens, about 50 ms). No page, an empty answer from every page, or 1.5 s (`OASIS_EYES_MS`) and the text goes out alone. Messages keep their order while one waits. `eyes` is in the roster and the snapshot; default on when the name matches `/anorak/i`, off otherwise; `setEyes {agentId, on}` switches it. The caption block is stripped from the thread (`normalize.js`). `node scripts/smoke.mjs eyes` (2 haiku turns, the script plays the page): 8/8. Bridged desktop sessions get no picture: a mod's `$.prompt.submit` carries text only (its `attachments` list is the engine's to set, and pasted images are not expanded for a plugin's prompt). The way around would be a file the session reads (one tool call per message), or the session calling `screenshot_viewport` itself.
- **Restarts** (2026-11-16, 2.1.323). What a restart used to cost: every agent came back at its desk with its session, but one that was mid-turn came back as "error: stopped mid-turn" and waited for someone to say "carry on", and a message written to an agent while its turn ran was gone (it waits inside the CLI process and dies with it; the transcript only has a `queue-operation enqueue`). Now:
  - **The journal** (`src/journal.js`, `data/agent-engine.journal.local.json`, next to the roster): written the moment something changes. It holds each message from `send` until the CLI echoes it (uuid, text, picture paths, `source`), bridge inboxes, Telegram updates taken but not yet handed to an agent, the agents that owe a reply on Telegram, a sign of life every 15 s, and the goodbye of a planned stop. The roster keeps `turnOpenAt` (mid-turn) and the agent's `pid`.
  - **A planned stop** (the `shutdown` command, Ctrl+C, SIGTERM, the console window closing = SIGHUP on Windows, Ctrl+Break) writes the roster and the goodbye, and logs who is mid-turn. An uncaught exception writes "crash: ..." before the process exits. Anything else (taskkill /F, power, Windows Update) leaves no goodbye and is dated by the last sign of life.
  - **At start** (`restoreRoster`, `src/resume.js`): an agent is mid-turn when the roster says so, unless the end of its transcript shows the turn still ended; after an unplanned stop the transcript alone can say so too (an assistant record that stopped for a tool, or a tool result with nothing after it). Each such agent is resumed and told once: "The engine restarted while you were working. Carry on from where you stopped." (`user.sent` with `auto: "resume"`, status reason "resumed after the engine restart", `resumedAt` in the snapshot until that turn ends: the sign reads "working · resumed"). Then its queued messages go out again, in order, under their old uuids. A uuid already in the transcript is crossed off instead, so restarting twice delivers nothing twice; a note that was taken in and cut off again gets a new note. `OASIS_RESUME=0` turns the note off (the agent then waits as before).
  - **Telegram**: an update is in the journal from `getUpdates` until it is handled, so a stop in between no longer loses it (the offset is confirmed first); it is tried at two starts at most. A message handed to an agent carries `source: "tg:<update id>"`. An agent that owed a reply still owes it for 15 minutes after the restart: the turn it is resumed into answers on Telegram. "X stopped before answering" is no longer sent while the engine itself closes.
  - **`/health` and hello** carry `restart: {startedAt, stop: {at, planned, reason}, resumed: [{id, name}], redelivered, line}`; `line` reads "restarted at 18:02, 1 agent resumed" (the HUD's engine pill shows it for 30 minutes, amber after an unplanned stop). The `restartInfo` command returns the same.
  - **Seen when a test engine was killed with a Bash call running**: its claude child exits by itself within 3 s (stdin closes); the transcript ends on the `tool_use`; `--resume` plus the note makes the model run the cut call again and finish; one `init`, no turn closes by itself. At start the engine still waits up to 5 s for the last run's pid if it holds the session, then stops it.
  - `node scripts/restart-smoke.mjs` (3 haiku turns, its own engines on port 4543: a kill mid-turn with a message queued, a planned stop, a restart on top of a restart): 18/18.
  - **Not covered:** the engine being down. Telegram messages wait at the bot until it is back (2026-11-15: the engine was off from the afternoon until 21:39, three messages arrived 2.5 h late). That needs something that starts the engine again (a watchdog or a Windows task), not this.
- **Characters** (2026-11-17, 2.1.323). Every agent has a card: `data/characters/<session id>.md` (`src/character.js`; `OASIS_CHARACTERS` moves the folder). The header's `name, voice, look, avatar, world, home, place` are the engine's (the Oasis page reports body, voice, world and surroundings with the `presence` command, `VillagePresence.tsx`); `role` (a sentence) and the text under the header ("who you are") are the owner's or the agent's own words, edited in the agent's settings menu, with `scripts/me.mjs`, or in the file itself (it is read fresh each time).
  - **How the agent learns it:** a note `[Oasis you: …]` (about 200 tokens) rides with the owner's message, the way the voice note does, because a system prompt appended at launch never reaches a resumed session (see `voice.js`). It goes with the first message after each start of the agent's process, again when the words, the look or the world changed (`cardStamp`), and after a compaction. The thread hides it. Seen: a haiku sandbox agent said its name, its avatar's look and what stands around its desk without a tool, and knew the owner's edit on the next message.
  - **Looks** (`src/looks.js`): one description per avatar file, made once from its gallery thumbnail by a one-shot `claude -p --model haiku` shown the picture (about 3 s, half a cent), kept in `data/characters/_looks.json`. `OASIS_LOOKS=0` turns it off.
  - **Pictures on request, not in every turn:** `node scripts/me.mjs look` (the agent's own avatar from the front, 512x640) and `around` (four 640x360 pictures: ahead, right, behind, left). The engine's `view` command asks an open Oasis page (`view.request` / `viewFrames`, rendered by `VillageEyes.tsx` from where the body stands right now), saves them under the temp folder and prints the paths; the agent reads the files. About 150 ms. Without a page, `look` gives the gallery thumbnail and `around` says so. Why on request: a picture is 300 to 700 tokens; four with every message would be about 2,000 tokens a turn for every agent all day, and most turns are about code. The place is in the card as one line of words instead (`village-place.ts`: distance to the plaza, neighbours, the nearest things with distance and direction), and eyes (one picture per message) stay a per-agent switch.
  - `scripts/me.mjs card | look | around | who "<text>" | role "<sentence>"`: who is asking comes from `OASIS_AGENT_ID` (the engine sets it), or `--agent <name, agent id or session id>` for any other kind of agent with a shell.
  - **Sessions the engine does not run** (watched, with the Oasis mod): a message sent to them from the Oasis carries the note inline, with the first one of an engine run and when the card changed (the mod only carries text). The mod also asks `POST /bridge/character {sessionId}` and hands the note beside a prompt typed in that window (`prompt.submit` context); **that part did not arrive in `claude -p` (stream-json and a command-line prompt both answered UNKNOWN), and is not seen in the desktop app yet.**
  - **Kinds checked on a test engine (haiku, sandbox):** a new agent, a resumed session, a fork, and a watched session with the mod each called `get_world_info` without a card and loaded `screenshot_viewport`, `screenshot_avatar`, `place_object`, `self_craft_scene`, `modify_object`, `remove_object`. A watched session whose own process has no Oasis plugin has no world tools and cannot be talked to. The MCP screenshot modes that take a subject (`agent-avatar-phantom`, `screenshot_avatar`) only know avatars placed in the world (Merlin, Anorak Pro), not village agents: for its own view a village agent uses `me.mjs`.
  - **Worlds today:** the village is the same list of agents in every world, at the same coordinates around the spawn point (`resolveVillageOrigin(null)`, one seat memory for all worlds). Seen: the same sandbox agent stood 7 m from the plaza in "Oasis Dusk" and in "The Oasis"; its card's `world` and `place` followed the page, `home` kept the first.
- **Results as files** (2026-11-17). Both notes (the engine's `[Oasis you: …]` and the plugin's "The Oasis" section) say: to show the owner a picture, an audio file, a video or a document, send it with SendUserFile (it plays or opens in the thread); a path alone is not enough. **Where SendUserFile exists** (2.1.323, init tool list): engine agents of every kind (new, resumed, fork: one spawn path sets `CLAUDE_CODE_ATTACHMENTS_BY_PATH=1`); a plain `claude -p` session only with that variable set, and without it the tool is absent. A session in another window gets the line from the plugin only when its tool list has SendUserFile (`prompt.compose` reads `e.tools`), and the engine leaves the line out of the note it sends such a session. **Not checked:** whether the desktop app offers SendUserFile to its own sessions; if not, the owner's desktop sessions get no line and have no way to put a player in the thread, short of setting the variable where the app starts.
- **Schedules** (2026-11-18, `src/schedule.js`). An agent can wake up on its own. Per agent, in the roster: `schedule {every: off | hourly | 3h | 6h | daily | weekly, at "HH:MM", day 0-6, prompt, since}`, `appointments [{id, at, repeat: null | daily | weekly, note, prompt, by}]`, `wake {lastAt, day, count}`. For all agents, in `data/agent-engine.schedule.local.json`: quiet hours (default 01:00-08:00) and a daily cap (default 8).
  - **When it fires:** the scheduler looks every 15 s (`OASIS_SCHEDULE_TICK_MS`) and when a turn ends. A due slot or appointment wakes the agent when it is idle (no turn, nothing queued, no open decision); busy, it waits for the turn to end. Never more than one scheduled message queued per agent; everything due at once goes as one message. Missed slots collapse into one wake-up (the engine off for five hours: one at start). The scheduler starts 20 s after the roster is back (`OASIS_SCHEDULE_START_MS`), so a carry-on note goes first.
  - **Quiet hours and the cap hold back the recurring wake-ups only.** A slot in the quiet hours is skipped; one missed while the engine was off goes out when they end. An appointment fires at its time whatever the cap and the quiet hours, because the Council at 16:20 must not lose to a cap spent on hourly wake-ups; it counts in the day's number. A one-off appointment more than a day late is dropped with a notice; a repeating one fires once and moves to its next time.
  - **The message:** `[Oasis schedule: <what>, <time>. This message comes from your schedule, not from the owner. To tell the owner on Telegram: node "<tell.mjs>" "<a few lines>".]`, then the agent's own standing prompt or `DEFAULT_PROMPT` (the owner's words), or the appointment's prompt or note. Late: "due 09:00 (sent 18:02: the engine was off or you were busy)". No eyes picture. `user.sent` has `auto: "schedule", scheduled: <label>`; the normalizer tags it in history read back from the transcript too; the thread shows a "scheduled" tag and hides the note. The turn it starts ends with `turn.end scheduled: true` unless someone else wrote during it; the page then does not mark it "finished, unseen", so the agent does not walk up to the owner for it (a decision or an error still shows as such). Telegram does not answer a scheduled turn.
  - **The work counter:** the owner's time comes from his own input only (keys, mouse, dictation), so a scheduled turn never counts as his. It counts in the agent's own hours, as its work.
  - **Commands** (WebSocket and `POST /api/cmd`): `setSchedule {agentId|agent, every?, at?, day?, prompt?}`, `addAppointment {agentId|agent, at, repeat?, note?, prompt?, by?}` (`at`: "16:20", "wed 16:20", "tomorrow 9:00", "2026-11-25 16:20", "in 30m", ms, ISO), `removeAppointment {agentId|agent, id}`, `wakeNow {agentId|agent, prompt?, by?}`, `listSchedules`, `scheduleSettings {quiet?: {from, to} | null, dailyCap?}`, `tellOwner {agentId|agent, text}` (Telegram, once per agent every 30 min). `scripts/schedule.mjs` wraps them (`list | set | prompt | add | remove | wake | settings`), `scripts/tell.mjs "<text>"` is the agent's way to tell the owner. Snapshots carry `schedule, appointments, nextWake {at, label}, wakesToday, scheduledRun`.
  - **Tests:** a fake clock for test engines only (`OASIS_FAKE_CLOCK=1`, never on 4530): the `clock {advanceMs | at}` command, `OASIS_CLOCK_OFFSET_MS` to start ahead. `node scripts/schedule-smoke.mjs` (its own engines on 4545, about 6 haiku turns): hourly, busy, an appointment, quiet hours, the cap, five hours off: 15/15.
- **One writer per session** (2026-11-08). A session is its transcript, and whichever process has it open holds the pen. Two holders each keep their own copy of the conversation in memory, and the transcript branches. `spawnAgent({sessionId, move:true})` stops the other holder first (only if idle; it waits up to 6 s because the registry flips to idle a moment after a turn), checks it's a claude process, then resumes the same session. Every 2 s the engine checks `~/.claude/sessions/*.json`. When a session it drives is opened by another process (you typed in the desktop app again), it stops its own process at once and watches the transcript instead. Both sides resume from the file, so neither loses a turn. `node scripts/smoke.mjs handoff` (two engines, 3 haiku turns): move keeps the id, the moved session remembers the earlier turn, a plain `claude --resume` sees the Oasis turn, and the transcript doesn't branch. **Not yet seen:** what the desktop app's window shows after its process is stopped and when you type there again.
- **Bridge: the same live session in two windows** (2026-11-09). A session that runs the Oasis plugin's mod (`plugins/oasis` at the repo root) checks in at `POST /bridge/poll` every second. Once the Oasis watches it, its snapshot says `bridged: true, readOnly: false`, and `send` queues the text in `src/bridge.js`. The mod collects it and calls `$.prompt.submit`, so the text becomes a turn of that same process. The desktop app keeps running it, and both windows show one conversation. The transcript records it as "The oasis plugin sent a message: …" (origin `{kind:'plugin', name:'oasis'}`), framed as starting the turn in the user's place. While the session replies, the mod's `turn.step` hook posts the text to `POST /bridge/event`, so the Oasis shows it word by word. `node scripts/bridge-smoke.mjs` (2 haiku turns, a test engine, a `claude -p --plugin-dir plugins/oasis` standing in for the desktop app): 8/8. **Not seen yet:** the desktop app loading the mod. Load it with `CLAUDE_CODE_PLUGIN_DIRS` in the `env` of `~/.claude/settings.json`, or with a local marketplace install.
- **Telegram: the owner's phone line** (2026-11-11, `src/telegram.js`). The engine is the one `getUpdates` consumer of the bot in `data/anorak-pro-telegram.local.json` (@anorakprobot; the Next app keeps `pollingEnabled: false` there and only sends; never also run `pnpm dev:telegram` on the same bot). Long poll 25 s; our offset and the pings switch live in `data/agent-engine-telegram.local.json`, and an update is confirmed before it is handled. Only the config's `chatId` is heard. "Tyler: fix the intro", "@tyler fix the intro" and, for voice, "Tyler, fix the intro" go to the agent whose name starts with that (case-insensitive, punctuation ignored); anything else goes to the agent whose name matches `/anorak/i`. The text reaches the agent through `send` (owned and bridged alike) as `[Telegram] …`. When a turn that took such a message ends, its last main-thread text goes back (name in front unless it is Anorak; Telegram HTML from the markdown, plain text if Telegram refuses it; split under 4096) and the files it sent with SendUserFile follow as photos or documents. `/agents`, `/stop [name]`, `/pings on|off`, `/help`. Voice notes: ElevenLabs Scribe (`scribe_v2`, the key `ELEVENLABS_API_KEY` from `C:/cb_video/claude/.env` like `C:/8f_dirk/scribe.py`, the village's names as key terms), echoed as "heard: …", then routed like text. **Pings:** an agent at `needs-decision` or `error` for 2 minutes gets one message per state change ("🟠 Tyler needs you: allow Bash: npm test?"), except a question its Telegram reply already carried and old transcript lines an observer replays. Only the engine on 4530 runs it; `OASIS_TELEGRAM=1|0` forces it on or off, and `OASIS_TELEGRAM_API/_CONFIG/_STATE/_PING_MS` point it elsewhere for tests. `{cmd:"telegram"}` reports its state (`pings: true|false` switches). The token never reaches a log line. **Daily check-in** (2026-11-16, `src/checkin.js`): at 21:00 local the line sends the day's work from the Mindcraft work counter (`GET http://127.0.0.1:4516/api/village/work`, `OASIS_WEB_URL`): time against the vow, XP, the vow's stake, where the XP came from, time per agent, the week. Kept: the numbers and a dry "well done"; short: "You sucked today", by how much, and whether the rest of the day can still make it (the owner asked for that tone; it is about the work only). ## Hermes agents (a second runtime)

`spawnAgent {name, cwd, runtime: "hermes", hermesHome?, command?, model?, permissionMode?}` starts a Hermes Agent (Nous Research) instead of Claude Code: `src/hermes.js`, one long-lived `hermes acp` process spoken to with the Agent Client Protocol (JSON-RPC, one message per line on stdin/stdout). It has the same methods and emits the same events as `agent.js`, so the page, the journal, schedules, voice and Telegram treat it like any owned agent; snapshots and the roster carry `runtime: "hermes"`.

- **Which Hermes:** `command` (an argv array, e.g. `["ssh", "og", "hermes", "acp"]` for one on another machine), else `OASIS_HERMES_BIN`, else the Windows installer's `%LOCALAPPDATA%\hermes\hermes-agent\venv\Scripts\hermes.exe`, else `hermes` on PATH. `hermesHome` sets `HERMES_HOME` (a profile folder, or a sandbox); without it Hermes uses its own default home and model.
- **Mapping:** `agent_message_chunk` → `text.delta` / `text`; `tool_call` / `tool_call_update` → `tool.start` / `tool.end` (`mcp_oasis_x` is shown as `mcp__oasis__x`); `plan` → `todo`; `usage_update` → `context`; `session/request_permission` → `permission.request` (allow → `allow_once`, allow always → `allow_session`, deny → `deny`; **Hermes denies by itself after 60 s**); `interrupt` → `session/cancel`; `setModel` → `session/set_model`; `setPermissionMode` → `session/set_mode` (`default`, `accept_edits`, `dont_ask`). No effort, no Chrome. Thinking text (`agent_thought_chunk`) is not shown. ACP reports no price: `costUsd` is 0.
- **One prompt at a time:** ACP has no mid-turn messages, so what the owner sends during a turn waits in the engine and goes out as one prompt when the turn ends (`user.consumed` then, never `folded`). A slash command (`/compact`, `/reset`) always goes alone: Hermes reads whatever follows it as its arguments.
- **Restarts:** the roster keeps the Hermes session id; at start the engine calls `session/load`, which replays the old conversation (shown as history) and continues it. **Hermes saves a conversation only when its turn ends**, so a turn's messages stay in the journal until then: a turn cut off by a stop or a crash keeps `turnOpenAt`, and at the next start the agent is told to carry on and gets those messages again under their old uuids. A process that cannot open a session (for example a model under 64K context) is stopped and its sign shows why; the next message tries again. A permission card nobody answers goes away after 60 s (`permission.resolved behavior: expired`), when Hermes has denied it by itself.
- **World tools:** Hermes never asks before an MCP call, so it does not get the Oasis MCP route directly. It gets `src/worldproxy.js` as a stdio MCP server: it forwards to `/api/mcp/oasis` and lists only the free tools of `worldtools.js` (27: looking, placing, moving, lighting, screenshots); a call to anything else gets an error result and never reaches the Oasis. Batches are split and checked part by part, only known MCP methods pass, and a session the Oasis forgot (2 h idle, a page-server restart) is opened again. A Hermes started with `command` (another machine) gets no world tools yet. **Not a sandbox:** Hermes's terminal runs any command outside its list of dangerous ones without asking (`approvals.mode: manual` asks only for those), so a Hermes agent could `curl` the MCP route itself, and do much else on this PC; the route has no key unless `OASIS_MCP_KEY` is set. A Hermes agent has the reach of a Claude Code agent with every Bash call allowed.
- **Seen** (Hermes 0.15.1, Windows, Ollama `qwen35-9b-agent` with 64K context, which Hermes requires): a fresh session without world tools is about 10.5K tokens of prompt (21K with every Oasis tool, measured in a probe); a short turn with one free world tool (two model calls) read 34.8K input tokens and took 27 s. `node scripts/hermes-smoke.mjs` (its own engine on 4545, a sandbox Hermes home in the temp folder, about five local turns, no money) covered a reply, a world tool, a refused tool, a restart with memory and a card that expires (19/19 on the real Hermes; its last phase died with the machine's GPU taken by other jobs, when a model call took 3 minutes). `node scripts/hermes-runtime-smoke.mjs` runs the runtime against `scripts/fake-acp.mjs`, a fake ACP agent (no model, about 40 s): queueing, a slash command alone, interrupt, allow always, a planned restart mid-turn with the carry-on note and the message delivered again, a start that cannot open a session: 20/20. `node scripts/worldproxy-smoke.mjs` (no model): the proxy's filter, batches, unknown methods, a forgotten session: 8/8. **Not exercised yet:** a permission card answered from the page, pictures, a Hermes on another machine. **Seen:** when its main model is slow, Hermes's side jobs (session titles) fall back to OpenRouter and Nous; with no keys nothing is spent, but a profile that has keys could pay for them. Its `auxiliary` section (per job: `provider: auto` by default) is where to pin them to the main model; not tried.

## Event schema v1

Every event is `{ v: 1, agentId, ts, kind, ...payload }`. The envelope fields always win over the payload.

| kind | payload |
|---|---|
| `init` | `sessionId, model, permissionMode, cwd, tools[], mcpServers[{name,status}], agents[], claudeCodeVersion`. Emitted again only when one of these changes (the CLI re-sends init every turn) |
| `meta` | `models[{value,resolvedModel,displayName,supportsEffort?,supportedEffortLevels?}], subscription, claudeCodeVersion, permissionMode, resolvedEffort` (from `initialize` + `get_settings`), or `title` (observe) |
| `status` | `status: working \| waiting \| needs-decision \| error \| idle`, `reason` |
| `user.sent` / `user.consumed` | `uuid, text, midTurn, priority, eyes? (a picture from the avatar went with it)` / `uuid, folded (true = taken into the running turn), waitedMs` |
| `user` | `text, uuid, replay`: a prompt seen in the stream or a transcript |
| `text.delta` / `text` | `messageId, index, text, parentToolUseId` / `messageId, text, parentToolUseId, model` |
| `tool.start` / `tool.end` | `toolUseId, name, input (clipped), summary, parentToolUseId` / `toolUseId, name, isError, output (clipped)` |
| `todo` | `source: TodoWrite \| Task`, `todos[{content,status,activeForm}]`: the whole list every time |
| `subagent.start` / `.progress` / `.end` | `toolUseId, taskId, description, subagentType, prompt` / `lastToolName, usage` / `status, summary, usage` |
| `permission.request` / `.resolved` / `.denied` | `requestId, requestKind: permission \| question \| plan, toolName, toolUseId, input, summary, suggestions, readOnly?` / `requestId, behavior` / `toolName, message` (an auto-deny) |
| `turn.end` | `subtype, isError, outcome: done-waiting \| needs-decision \| error, reason, result, durationMs, durationApiMs, numTurns, usage{input,output,cacheRead,cacheCreation}, costUsd (this turn), totalCostUsd (process total), contextTokens, contextWindow, model, permissionDenials[], terminalReason, stopReason, notices?` |
| `context` | `usedTokens, maxTokens, percent, model` (from `get_context_usage` after every turn; costs no quota) |
| `rate_limit` | `status, utilization, resetsAt, window` (the subscription's 7-day window) |
| `notice` / `error` / `exit` / `model` / `mode` / `effort` / `eyes` / `hook` / `removed` | misc: interrupt, compaction, model fallback, process exit and stderr, model switch (`resolvedEffort` too), eyes switch (`eyes`), permission-mode switch (`permissionMode`), effort switch (`effort` or null for the default, `resolvedEffort`, `applied:"on next start"` when the process is down), a hook fired for an owned agent, agent removed (its backlog is dropped; later events for that id are ignored) |
| `user.consumed` with `dropped` | a pending message that will never be echoed: `expired` (a whole turn passed), `dropped by interrupt` (not in `still_queued`) or `cancelled`. Keeps an agent from staying `working` forever |

`reason` on a `turn.end` is one of `end_turn`, `interrupted`, `permission`, `permission-denied`, `question`, `question-text`, `plan`, or the error subtype. `needs-decision` covers: a `can_use_tool` request still open (permission, AskUserQuestion, ExitPlanMode), an auto-denied tool (`permission_denials` the host did not answer itself), a pending AskUserQuestion or ExitPlanMode tool call, or, as a heuristic, a final text ending in `?`.

**Status machine (owned agents):** `idle` after spawn, then `working` from the send until the `result` while queued messages remain, `needs-decision` while a `can_use_tool` is open, then `waiting`, `needs-decision` or `error` from the outcome. An interrupt resolves to `waiting`. A non-zero exit is `error`. A killed agent is `idle`.

**WebSocket** `ws://127.0.0.1:4530/ws`: on connect you get `{type:"hello", agents, backlog}`. Then come `{type:"event", event}` and `{type:"agents", agents}` (snapshots). Send `{id, cmd, ...args}` and you get `{type:"reply", id, ok, data|error}`; a control request that resolved to `{ok:false, error}` (setModel, setPermissionMode, interrupt) comes back as `ok:false`. Permission requests carry the tool input unclipped (up to 256 KB of JSON), so the owner reviews exactly what will run. Sending a message while a permission / question / plan is open keeps the agent `needs-decision`, and an interrupt only applies to the turn it was sent in. Commands: `listAgents, listSessions, listLive, spawnAgent{name,cwd,sessionId?,model?,permissionMode?,effort?,fork?,force?}, send{agentId,text,priority?}, interrupt{agentId,cancelQueued?}, setModel{agentId,model}, setPermissionMode{agentId,mode}, setEffort{agentId,effort: low|medium|high|xhigh|max|null}, setEyes{agentId,on}, canSee{on}, eyesFrame{requestId,data?,mediaType?}, respond{agentId,requestId,behavior:"allow"|"deny",answers?,always?,message?}, contextUsage, kill{agentId}, restart, restartInfo, presence{agents}, getCharacter{agentId|agent}, setCharacter{agentId|agent,role?,who?}, view{agentId|agent,view:look|around}, viewFrames{requestId,pictures}, observe{sessionPath}, unobserve, history, telegram{pings?, checkin?, checkinTime?}, shutdown`. `POST /api/cmd` takes the same JSON. The server binds 127.0.0.1 and refuses non-localhost `Origin`s. There is no auth, which is fine for a spike, not for a product.

## FINDINGS

Spend: **17 short turns** (16 haiku, 1 sonnet), about $0.12 at list price according to `total_cost_usd`. Everything else (initialize, get_context_usage, set_model, set_permission_mode, resume, observe) costs no quota.

**Process and protocol.** One `claude -p --input-format stream-json` process stays alive across turns until stdin closes (then exit code 0). Before the first user message it only emits `SessionStart` hook messages. **No `system/init` arrives until the first message, and init is re-emitted at the start of every turn.** Its tool count grew from 29 to 51 once the claude.ai MCP connectors finished connecting. Stdin user message: `{"type":"user","message":{"role":"user","content":"..."},"parent_tool_use_id":null,"session_id":"","uuid":"<client uuid>"}`. The client `uuid` comes back unchanged on the replay echo. Control channel: host → CLI `{"type":"control_request","request_id":"x","request":{"subtype":...}}`, answered by `{"type":"control_response","response":{"subtype":"success"|"error","request_id":"x","response":{...}|"error":"..."}}`. An unknown subtype gets `"Unsupported control request subtype: ..."`. Zero-cost requests verified: `initialize` (returns `commands`, `agents`, **`models` (13 entries with value, resolvedModel and supported effort levels)**, `account` (subscription type), `pid`, `current_permission_mode`, `session_state`), `get_context_usage`, `set_model`, `set_permission_mode`, `get_settings`, `get_status`, `mcp_status`. The binary also handles `end_session`, `cancel_async_message`, `rewind_conversation`, `fork_conversation`, `get_plan`, `side_question` and more. Those are untested.

**Mid-turn messages ("talk to it while it works"): works, two verified behaviours, no host-side queue needed.**
1. Sent while a tool runs, the message is **folded into the running turn at the next tool-result boundary**. Probe: `sleep 8` was running when "end with PINEAPPLE" was sent at t+3.4s. The echo (`isReplay:true`) arrived right after the tool_result at t+11.6s, and the same turn answered `first-done\nPINEAPPLE`. One `result` with `num_turns:2`. The engine repeated this over WebSocket (KIWI, `user.consumed folded:true, waitedMs 11619`).
2. Sent while the model streams plain text (no tool boundary left), the message **queues and runs as the next turn** right after the `result`. A new `system/init` comes first, then the echo, then a second `result`. Probe: BANANA. In the UI: MANGO was sent just after the tool finished, so it showed "ran as the next turn".
- So one result does not mean one message. The engine tracks sent-but-not-echoed uuids and keeps the avatar `working` until all are consumed.
- The CLI also supports `priority: "now"` on a user message ("stop the turn at its next model request and answer this", running shell commands are backgrounded) and `"later"`, plus `interrupt {send_now:true, message_uuid}` and `cancel_async_message {uuid}` (from the schema in the binary, advertised in init `capabilities: interrupt_send_now_v1, interrupt_cancel_queued_v1, msg_lifecycle_v1`). The engine passes `priority` through (the UI "urgent" checkbox). **`"now"` itself was not exercised (no turn spent on it).**

**Interrupt: works.** `{"subtype":"interrupt"}` → `{"still_queued":[]}` (queued uuids that will still run; add `cancel_queued:true` to drop them). Then `[Request interrupted by user]` (or `... for tool use`) and a `result` with `subtype:"error_during_execution"`, `is_error:true`, `terminal_reason:"aborted_streaming"` (during generation) or `"aborted_tools"` (during a running Bash call; that tool_result is an error saying the call was stopped). The process stays usable. The engine maps this to `outcome done-waiting, reason interrupted`. Side finding: the Bash tool **refuses long foreground sleeps** (`sleep 40` gave "Blocked: sleep 40 followed by: echo late"), so use something like `node -e "setTimeout(...)"` for slow test commands.

**Model switching: no respawn needed.** `{"subtype":"set_model","model":"sonnet"}` → `{"model":"claude-sonnet-5-5"}`, plus a synthetic `<local-command-stdout>Set model to sonnet (claude-sonnet-5-5)` echo. The next turn's init and assistant messages said `claude-sonnet-5-5`, and `result.modelUsage` listed both models. Aliases resolved in this account: `haiku` → `claude-haiku-5-5`, `sonnet` → `claude-sonnet-5-5`, `default`/`opus` → `claude-opus-5-5` (full list from `initialize.models`). **Effort switching: live, no respawn** (2.1.318, 2026-11-09). `{"subtype":"apply_flag_settings","settings":{"effortLevel":"high"}}` → success, and `{"subtype":"get_settings"}` then reports `applied.effort:"high"` on the same pid. In `-p` mode the handler merges the key into the flag-settings layer and sets the session's effort (the same path `/effort` uses); it applies at once, also mid-turn (the next model request uses it). `effortLevel:null` goes back to the default (`medium` for haiku-5-5 here). **An unknown level is acknowledged with success and ignored**, so the engine reads the level back with `get_settings` and refuses a mismatch. `initialize.models[]` lists `supportsEffort` and `supportedEffortLevels` per model: the 5.x models and opus-4-7/4-8 take `low, medium, high, xhigh, max`; opus-4-6 and sonnet-4-6 have no `xhigh`; haiku-4-5 has no effort at all. `setEffort` on a stopped agent stores the level for its next start (`--effort`). `node scripts/smoke.mjs effort` (0 turns): 13/13. `set_max_thinking_tokens` also exists; not used.

**init carries** `session_id, cwd, model, permissionMode, tools[], mcp_servers[{name,status}], slash_commands, agents, skills, plugins, claude_code_version, apiKeySource, capabilities, messaging_socket_path, fast_mode_state`. Permission mode names: `--help` lists `acceptEdits, auto, bypassPermissions, manual, dontAsk, plan`. **`--permission-mode default` is still accepted.** Both `default` and `manual` report `current_permission_mode: "default"`.

**Permission prompts via host: works, but only with the hidden flag `--permission-prompt-tool stdio`.**
- `--permission-mode default --permission-prompts host` alone (host is the default) gives **no** control request. Writes were auto-denied with `system/permission_denied` ("Claude requested permissions to write to ..., but you haven't granted it yet.") and listed in `result.permission_denials`.
- Adding `--permission-prompt-tool stdio` (what the Agent SDK passes when `canUseTool` is set; found in the binary) makes each prompt arrive as `{"type":"control_request","request_id":"<uuid>","request":{"subtype":"can_use_tool","tool_name":"Write","display_name":"Write","input":{...},"description":"perm-a.txt","permission_suggestions":[{"type":"setMode","mode":"acceptEdits","destination":"session"}],"tool_use_id":"toolu_..."}}`.
- Allow: `{"type":"control_response","response":{"subtype":"success","request_id":"<same>","response":{"behavior":"allow","updatedInput":{...}}}}`. Add `"updatedPermissions":[<a suggestion>]` for "allow always".
- Deny: `{... "response":{"behavior":"deny","message":"..."}}`. The model sees the message as the tool_result, and the result's `permission_denials` lists it (the engine doesn't flag host-denied calls as needs-decision).
- Verified: allow created `perm-a.txt`, deny left `perm-b.txt` absent. A pending AskUserQuestion request sat about 3.7 minutes and was still answerable (no timeout seen).
- The engine always passes `--permission-prompt-tool stdio`. Agents use the mode the owner picks per agent, or with no `--permission-mode`, the owner's settings (`defaultMode: auto` on this machine). bypassPermissions is not forced.

**AskUserQuestion / ExitPlanMode.** Without a prompt handler these tools are **not offered at all** in `-p`. With `--permission-prompt-tool stdio` the init tools gain `AskUserQuestion, EnterPlanMode, ExitPlanMode`. A question arrives as `can_use_tool` with `tool_name:"AskUserQuestion"`, and the input has `questions[{question, header, options[{label,description}], multiSelect}]`. Answer with `behavior:"allow"` and `updatedInput:{...input, answers:{"<question text>":"<label>"}}`. The tool_result was `Your questions have been answered: "Do you prefer tea or coffee?"="Tea"` and the agent replied `Tea`. Verified over WebSocket. Agent status was `needs-decision` while it waited. ExitPlanMode should go the same way. Not exercised.

**Subagents (Agent tool; init still lists it as `Task`).** The parent emits `tool_use name:"Agent"` with input `{description, prompt, subagent_type, run_in_background}`. Then come `system/task_started {task_id, tool_use_id: <Agent tool_use id>, task_type:"local_agent", subagent_type, is_backgrounded, spawn_depth, prompt}`. Every subagent message carries **`parent_tool_use_id = the Agent tool_use id`** plus `agent_id, subagent_type, task_description`. That covers its prompt, tool_use (`Glob`), tool_result, and text (text needs `--forward-subagent-text`). Then `system/task_progress {last_tool_name, usage}`, `system/task_updated {patch:{status:"completed"}}`, `system/task_notification {status, summary, output_file, usage}`, and the parent's tool_result with `tool_use_result {status, agentId, agentType, toolsUsed, ...}`. `result.subagent_stats` counts spawned, completed and failed. Bash calls are tasks too (`task_type:"local_bash"`). Agents default to background (`run_in_background` defaults true). The engine ends a subagent on `task_notification`, or on the tool_result when it was foreground. Subagent transcripts live in `<session>/subagents/agent-<id>.jsonl` + `.meta.json`.

**Todos.** With 5.x models, **TodoWrite is not available in `-p`** (`ToolSearch select:TodoWrite` → "No matching deferred tools found"). `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` did not change that. The model uses the deferred **TaskCreate / TaskUpdate** tools instead (`TaskCreate {subject, description, activeForm}` → "Task #1 created", `TaskUpdate {taskId:"1", status:"completed"}`). The normalizer maps both shapes to `todo` events with the whole list. Verified: wait/answer went pending → completed. (The desktop app uses its own plan tool via MCP, so a real Oasis may want its own todo tool too.)

**Usage, context, limits.**
- `result.usage` and `result.model_usage_since_last_result` are **per turn**. `result.total_cost_usd` is **cumulative for the process** (0.00345 → 0.00393 → 0.00439 ...).
- Each assistant message has `usage`. Context ≈ `input + cache_creation + cache_read` of the last main-thread message. `modelUsage[model].contextWindow` was 1,000,000 for haiku-5-5 and sonnet-5-5.
- `get_context_usage` gives the exact breakdown (`totalTokens`, `maxTokens`, `percentage`, `categories`, `memoryFiles`, `messageBreakdown`). A fresh sandbox session is about 22k tokens.
- `rate_limit_event` arrives once per turn with the **subscription 7-day utilization** (`0.67`, `resetsAt`). The UI shows it.
- `thinking_tokens` system messages give thinking progress. Thinking text itself is empty (`thinking:""` + signature).

**Resuming a session created elsewhere: works.** A one-shot `claude -p "Remember the codeword ZEBRA"` session (stand-in for "created in a terminal") was resumed by a stream-json process with `--resume <id>`. Same session id, no fork, and it answered `ZEBRA`. Transcripts from every entrypoint share one `.jsonl` format (`entrypoint` is `cli`, `claude-desktop`, `claude-vscode` or `sdk-cli`), so desktop or terminal sessions resume the same way. That part is inferred from the format, because no owner session was touched. `--resume` **found the session even from a different cwd** (the history loaded). The engine still spawns in the session's original cwd (from discovery), so tools and CLAUDE.md match. Caveats:
- A resume with no turn still **appends** to the transcript (`cost-state` / `last-prompt` records on exit). Only observe mode is truly read-only.
- `get_context_usage` right after `--resume` proves the history is loaded, and costs no quota. Restored roster agents measured 36.8k tokens against about 22k for a fresh session.

**Same session open in two places: it silently forks.** Two stream-json processes resumed the same id at the same time. There was no lock, no error and no auto-fork, and both wrote to the same `.jsonl`. Each keeps its own in-memory history: A never saw B's message. The transcript's `parentUuid` chain forked at the last shared record. The next fresh `--resume` followed the **last `last-prompt.leafUuid` written** (here B's branch, because B exited last), and A's exchange was orphaned. **Rule for the Oasis: never drive a session that another process has open.** Use observe, or `--fork-session`. The engine enforces this. `spawnAgent` refuses a session that is live in a foreign process (see the registry below) unless `fork:true` or `force:true`. Verified with a sandbox session held open by a foreign `claude -p`.

**Bonus: a live registry of every running session, at no cost.** Every Claude Code process, whether desktop app, terminal, `-p` or SDK (including the engine's own children), maintains `~/.claude/sessions/<pid>.json` = `{pid, sessionId, cwd, kind, entrypoint, name, status: "idle"|"busy", statusUpdatedAt, messagingSocketPath, peerFeatures, ...}`. Files of dead pids linger, so check the pid. The `<pid>.<hash>.key` files hold peer tokens, and the engine never reads them. `claude agents --json [--all]` prints the same data: `[{pid, cwd, kind:"interactive", startedAt, sessionId, name, status}]`. On this machine it showed 22 open sessions, all `kind:"interactive"`, with `idle`/`busy`. The engine uses the registry for exact "open elsewhere" detection in `listSessions` (`live` field, "open · busy" badge in the UI) and for observer status (busy → working, idle → waiting). `messagingSocketPath` (a named pipe, `peerProtocol:1`) looks like the channel desktop sessions use to message each other. It might let the Oasis talk to sessions it doesn't own. **Unexplored.** Not tested: `claude --bg` background agents and their working/blocked/done states (that would have spent turns).

**Observe mode (read-only tail): works**, against the owner's live desktop sessions and sandbox ones. It replays the last 512 KB of the transcript as events, then polls every second for appended bytes. It splits on `\n` at byte level and tolerates partial lines and giant records. Transcript records differ from the stream:
- one `assistant` record per content block
- no `result` record, so turn ends come from `system/stop_hook_summary` or `turn_duration`, and observed turns have no cost
- titles come from `custom-title` / `agent-name` records or `<session>/custom-title.json`
- `queue-operation` records show mid-turn enqueues
- the `.jsonl` interleaves both branches of a fork in file order

Status comes from records plus the live registry. Without a registry entry, "working" with no writes for 10 minutes becomes idle.

**Hooks over HTTP (third path): works except SessionStart.** Project-level `spike/sandbox/agent-b/.claude/settings.json` with `{"type":"http","url":"http://127.0.0.1:4530/hook"}` delivered `UserPromptSubmit, PreToolUse, PermissionRequest, Notification, PostToolUse, Stop, SessionEnd` to `POST /hook`. Answering `{}` (no decision) left the session's own behaviour unchanged, and the AskUserQuestion still reached our `can_use_tool` handler. **`SessionStart` did not arrive** at process start, though the owner's command-type SessionStart hook did run. Loopback URLs are explicitly allowed. Hook events for unknown sessions become read-only "hook" agents. For owned agents they only add a `hook` marker event.

**Session discovery.** 193 transcripts (7.2 GB, 107 over 5 MB) are listed in about 260 ms cold and 8 ms cached. Only a 128 KB head and tail are read per file. cwd comes from the first record that has one, and some sessions start with a >128 KB `file-history-snapshot`, so the tail is the fallback. Title order: `custom-title.json` → last `custom-title` → `agent-name` → `summary` → first real prompt. The encoded project dir is the cwd with every non-alphanumeric character turned into `-` (`C:\7c_oasis\spike` → `C--7c-oasis-spike`).

**Bare mode.** We never pass `--bare` (its help says auth is "strictly ANTHROPIC_API_KEY or apiKeyHelper"). Non-bare `-p` used the subscription: `apiKeySource:"none"`, `get_status` said "Claude Ultra account", and `rate_limit_event` showed the 7-day window. In 2.1.316 nothing suggests `-p` defaults to bare.

**What I verified, and what I didn't.**
- Engine: everything above was exercised with real turns or zero-cost control requests (probe logs in `spike/data/probe-logs`, gitignored).
- UI, in the desktop app's browser pane (screenshots): the scene renders; the 3D windows show live cards (text, tool calls, todos, subagent, turn end with cost and context); the status rings show all five colours (working green, waiting blue, needs-decision amber, error red, idle gray); clicking an avatar or a row focuses it and flies the camera there; the composer sent a turn and a mid-turn message; "observe" and the "open · busy" badges work.
- **Not checked in the browser:** answering a permission or question by clicking the window's buttons (the same `respond` command was verified over WebSocket), the "urgent" (`priority:"now"`) path, ExitPlanMode, and how it performs with more than six agents.
